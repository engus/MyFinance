# Cashflow: транзакции, регулярные шаблоны, сверка, HTTP API, UI

Дата: 2026-08-02
Статус: одобрено

## Контекст

Второй из пяти под-проектов приложения для домашней бухгалтерии (полный список — `docs/superpowers/specs/2026-08-02-foundation-design.md`). Фундамент уже реализован: ledger/account/category/reconciliation/rates сервисы, сессионная аутентификация, страницы логина/регистрации и заглушка дашборда. Ни один из этих сервисов пока не доступен по HTTP, и ни один UI кроме auth-страниц не существует.

Цель этого под-проекта — сделать первую реально рабочую часть приложения:
- HTTP API поверх уже написанных сервисов (accounts, categories, transactions, reconciliation).
- Логика генерации регулярных транзакций (шаблонов), которая была заложена в схему (`Transaction.frequency`/`interval`) в Фундаменте, но не реализована.
- Дефолтные категории при регистрации.
- Мягкое удаление (`isActive`) для счетов/категорий/шаблонов, у которых уже есть проводки.
- Cashflow-страница: список счетов, income/expense-транзакции, сверка остатков.

Вне скоупа: конвертация валют на дашборде (под-проект 4), UI активов (под-проект 3), настройки/аккаунт (под-проект 5).

## Модель "автоматической атрибуции"

Ключевое уточнение (согласовано в брейнсторминге): у приложения нет банковской выписки — при сверке есть только один агрегированный дельта-показатель на счёт за период. Поэтому "атрибуция" — это не эвристика над транзакционными описаниями, а следующий механизм:

1. Пользователь один раз регистрирует регулярный шаблон (например "Аренда, -$1000/месяц").
2. Перед каждой сверкой система догоняет шаблон: генерирует все просроченные конкретные проводки (occurrences) с момента последней генерации до сегодня.
3. Сверка считает дельту между введённым остатком и уже посчитанным балансом счёта (который теперь включает свежесгенерированные проводки). Необъяснённый остаток дельты уходит в `Other`, как и раньше (без изменений в `reconciliation.service`, кроме порядка вызовов).

Генерация запускается лениво — непосредственно перед сверкой конкретного счёта, без фоновых задач/крона (не нужно на масштабе одного пользователя и без инфраструктуры воркеров в проекте).

## Изменения схемы данных

`apps/api/prisma/schema.prisma`:

- `Transaction.templateId String?` — self-relation FK (`onDelete: SetNull`), проставляется только на сгенерированных occurrence-транзакциях, ссылается на породивший их `RECURRING`-шаблон.
- `Transaction.nextRunDate DateTime?` — заполняется только на шаблонах (`frequency = RECURRING`); продвигается вперёд при каждой генерации occurrence.
- `Transaction.isActive Boolean @default(true)` — имеет смысл только для шаблонов: `false` останавливает будущую генерацию, прошлые occurrences не трогает.
- `Account.isActive Boolean @default(true)`.
- `Category.isActive Boolean @default(true)`.

Прошлые occurrence-транзакции — обычные `ONE_OFF` транзакции с реальными `Entry`, видны и редактируются как любая другая транзакция; редактирование шаблона влияет только на будущие генерации.

## Генерация регулярных транзакций

`apps/api/src/modules/recurring/recurring.service.ts`:

```ts
function advance(date: Date, interval: RecurrenceInterval, customDays?: number): Date
// WEEK/MONTH/QUARTER/YEAR — календарная арифметика (не "+30 дней"),
// с учётом конца месяца (31 янв + месяц -> 28/29 фев).
// CUSTOM -> date + customDays.

async function generateDueOccurrences(prisma: PrismaClient, userId: string): Promise<Transaction[]>
// Для каждого активного RECURRING-шаблона пользователя с nextRunDate <= сегодня:
//   пока nextRunDate <= сегодня:
//     createTransaction(...) с frequency=ONE_OFF, templateId=template.id, date=nextRunDate
//     nextRunDate = advance(nextRunDate, template.interval, template.customDays)
// Возвращает список всех сгенерированных occurrence-транзакций.
```

Идемпотентность обеспечивается тем, что `nextRunDate` продвигается атомарно вместе с созданием проводки (в одной DB-транзакции); повторный вызов в тот же день не создаёт дублей, потому что `nextRunDate` уже в будущем.

### Интеграция со сверкой

`applyReconciliation` (Фундамент, без изменений в сигнатуре) вызывается только после `generateDueOccurrences(prisma, userId)` — это новый первый шаг в HTTP-хендлере `POST /api/accounts/:id/reconcile`, а не изменение самого `reconciliation.service`.

## Дефолтные категории

При регистрации (`registerUser`, уже вызывает `seedSystemCategories`) добавляется второй вызов `seedDefaultCategories(prisma, userId)`:

- Income: `Зарплата`, `Прочий доход`
- Expense: `Продукты`, `Аренда/Жильё`, `Авто`, `Коммунальные`, `Кредиты`, `Развлечения`, `Здоровье`, `Прочие расходы`

Это обычные (не системные) категории — пользователь может их переименовать, отключить (`isActive=false`) или удалить, если на них нет проводок.

## Мягкое удаление

Единое правило для `Account` и `Category`:
- `DELETE` без проводок → настоящее удаление из БД.
- `DELETE` с существующими проводками → `isActive = false` (мягкое удаление), запись пропадает из активных списков, но остаётся доступной по историческим проводкам.
- Системные категории (`isSystem = true`) всегда отклоняют `PATCH`/`DELETE` с `403`.

`Transaction` не получает такого правила для обычных (`ONE_OFF`) транзакций — они либо существуют целиком с проводками, либо удаляются целиком (каскадное удаление `Entry` уже есть в схеме). `isActive` на `Transaction` регулирует только шаблоны (`RECURRING`).

## HTTP API

Все роуты требуют `requireAuth`; мутирующие — дополнительно `requireCsrf`. Каждый запрос фильтруется по `req.userId`; попытка доступа к чужим данным — `404` (не `403`, чтобы не подтверждать существование чужой записи).

```
GET    /api/accounts                    -> список счетов с посчитанным балансом (listAccountsWithBalances)
POST   /api/accounts                    -> { name, kind, currency }
PATCH  /api/accounts/:id                -> { name?, currency? }
DELETE /api/accounts/:id                -> soft/hard delete по правилу выше

GET    /api/categories                  -> список (?includeInactive=true — включить отключённые)
POST   /api/categories                  -> { name, kind }
PATCH  /api/categories/:id              -> { name? } (kind неизменяем; isSystem -> 403)
DELETE /api/categories/:id              -> soft/hard delete по правилу выше; isSystem -> 403

GET    /api/transactions                -> ?kind=income|expense, ?frequency=ONE_OFF|RECURRING, ?accountId=
POST   /api/transactions                -> one-off: { description, date, entries: [EntryInput, EntryInput] }
                                            recurring template: { description, accountId, categoryId, amount,
                                                                   currency, interval, customDays?, startDate }
PATCH  /api/transactions/:id            -> id шаблона (frequency=RECURRING) -> правка amount/interval/isActive.
                                            id обычной ONE_OFF-транзакции (в т.ч. сгенерированного occurrence) ->
                                            правка entries, как у любой другой транзакции. Шаблон и его occurrences —
                                            разные записи с разными id, так что путаницы между ними нет.
DELETE /api/transactions/:id            -> ONE_OFF -> настоящее удаление (каскад Entry).
                                            RECURRING шаблон -> isActive=false.

POST   /api/accounts/:id/reconcile      -> { newBalance, date } -> generateDueOccurrences(userId), затем
                                            applyReconciliation; ответ { delta, applied, generatedOccurrences }
```

Валидация тела запроса — `zod`, тем же паттерном, что и в `app.ts` для auth-роутов. Дубликат имени категории у одного пользователя (`@@unique([userId, name])`) -> `409`.

**Валидaция валюты**: `EntryInput.currency`, указывающий на `accountId`, обязан совпадать с `currency` этого счёта (конвертации в этом под-проекте нет — она в под-проекте 4). Проверка добавляется рядом с существующим `InvalidEntryError` в `ledger.service`.

## Frontend — страница Cashflow

Макет (вариант **F**, выбран визуально в ходе брейнсторминга): две колонки Income/Expense слева, узкий сайдбар счетов справа.

`apps/web/src/pages/CashflowPage.tsx` + подкомпоненты:

- `IncomeColumn` / `ExpenseColumn` — список транзакций (описание, сумма, дата; у occurrence — значок ⟳ и период шаблона); "+ Добавить" открывает форму создания (переключатель one-off/регулярная, счёт, категория, сумма, валюта, дата/интервал).
- `AccountsSidebar` — карточка на счёт: имя, валюта, текущий баланс, действие "Сверить →", открывающее форму сверки (новый остаток) и показывающее итоговую дельту после отправки.
- Категории — выпадающие списки из `GET /api/categories`, отфильтрованные по `kind`; лёгкое управление (переименовать/отключить) — инлайн в выпадающем списке или маленькой модалке, без отдельной страницы настроек.

**Поток данных**: при загрузке страницы — параллельные запросы accounts/categories/transactions, затем рендер. Создание/редактирование/удаление транзакции или сверка — рефетч затронутых списков (без локального оптимистичного патчинга — оправдано низкой частотой операций и одним пользователем).

**API-клиент**: `apps/web/src/api/accounts.ts`, `categories.ts`, `transactions.ts` — тонкие обёртки над существующим `apiFetch`, тем же паттерном, что и `api/auth.ts`.

## Тестирование

**Backend unit-тесты** (`apps/api/tests/recurring.service.test.ts` и др.):
- `advance()` для WEEK/MONTH/QUARTER/YEAR/CUSTOM, включая конец месяца.
- Догон: шаблон не трогали 3 месяца -> генерируется ровно 3 occurrence за один вызов.
- Идемпотентность: повторный вызов в тот же день не плодит дубли.
- `isActive=false` шаблоны пропускаются.
- Интеграционный тест сверки: occurrence аренды генерируется, дельта в `Other` отражает только необъяснённый остаток.

**Route-тесты** (supertest, по образцу `auth.routes.test.ts`):
- Изоляция по владельцу — `404` при попытке доступа к чужому счёту/категории/транзакции.
- Системные категории отклоняют `PATCH`/`DELETE` с `403`.
- Дубликат имени категории -> `409`.
- Ветвление soft/hard delete (с проводками и без).

**Frontend-тесты**: `CashflowPage` рендерит колонки и сайдбар из замоканных ответов API; валидация формы добавления транзакции; форма сверки показывает возвращённую дельту.

## Обработка ошибок

- `400` — ошибки валидации `zod`.
- `403` — попытка изменить/удалить системную категорию.
- `404` — запись не найдена или принадлежит другому пользователю.
- `409` — дубликат имени категории.

## Демо-данные

Для ручного тестирования создан демо-пользователь (`demo@myfinance.app`), с несколькими счетами, категориями и one-off транзакциями через уже существующие сервисы Фундамента — не часть этого плана реализации, разовое действие для удобства проверки.

## Вне скоупа этого документа

- Конвертация валют и агрегация на дашборде — под-проект 4.
- Активы (`Account.kind = ASSET`) как отдельная страница/логика оценки — под-проект 3 (сама модель данных уже поддерживает `ASSET`-счета, что и использовано в демо-данных).
- Настройки/аккаунт, включая переключение `reconciliationMode` пользователя — под-проект 5.
- Управление категориями как отдельная полноценная страница (пока — инлайн в Cashflow).
