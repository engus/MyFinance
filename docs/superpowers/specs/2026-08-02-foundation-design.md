## Модель данных: упрощённая двойная запись

Полный chart of accounts (Assets/Income/Expense/Equity как единая иерархия счетов) избыточен для целей проекта. Вместо этого — три сущности:

### Account

Реальный счёт с балансом.

- `kind`: `FINANCIAL` (карта, банковский счёт, наличка) | `ASSET` (авто, недвижимость, ценные бумаги, и т.д. — второй под-проект)
- `currency`
- `balance` (текущий, производный от проводок + ручных сверок)

### Category

Метка дохода/траты. Не счёт, баланса не имеет, используется только для классификации проводок и отчётности.

- `kind`: `INCOME` | `EXPENSE`
- Системные категории (не удаляются пользователем, создаются автоматически при создании аккаунта):
  - `Other` — неразмеченный остаток при сверке
  - `Unrealized Revaluation` — переоценка активов без движения денег

### Transaction / Entry

Transaction — событие; состоит ровно из двух Entry (проводок). Каждая Entry ссылается либо на Account, либо на Category, с суммой и знаком. Инвариант двойной записи: сумма по дебету == сумме по кредиту — проверяется в бизнес-логике при создании транзакции (в рамках одной DB-транзакции).

`Transaction.frequency`: `ONE_OFF` | `RECURRING` (с `interval`: неделя/месяц/квартал/год/кастомное число дней). Recurring — шаблон, из которого в под-проекте Cashflow будут генерироваться конкретные проводки по расписанию. Поле закладывается в схему сейчас, логика генерации — вне скоупа этого документа.

### Примеры проводок

| Событие                                       | Entry 1                     | Entry 2                                     |
| --------------------------------------------- | --------------------------- | ------------------------------------------- |
| Зарплата                                      | `+Account(карта)`           | `+Category(Зарплата, income)`               |
| Крупная трата (авто, атрибутированная)        | `-Account(карта)`           | `-Category(Авто, expense)`                  |
| Покупка актива                                | `-Account(карта)`           | `+Account(авто, ASSET)`                     |
| Переоценка актива (+$500, без движения денег) | `+Account(портфель, ASSET)` | `+Category(Unrealized Revaluation, income)` |

Активы (`Account.kind = ASSET`) участвуют в той же двойной записи, что и финансовые счета — это значит, что весь цикл (покупка актива, изменение его стоимости) целиком представлен проводками, без отдельного нессвязанного реестра.

### Ежемесячная сверка остатков

Пользователь вводит новый остаток по Account. Система вычисляет дельту между введённым остатком и (предыдущий остаток + сумма проведённых за период транзакций по этому счёту). Ненулевая дельта — это непровизнесённые траты/доходы.

Обработка дельты — настраивается пользователем (per-user setting, значение по умолчанию — авто):

- **Авто (default):** дельта автоматически проводится в `Category(Other)` без подтверждения.
- **С подтверждением:** система показывает рассчитанную дельту, пользователь явно подтверждает перед созданием проводки.

## Мультивалютность

Каждый Account и Transaction хранит суммы в своей валюте. Для конвертации в валюту дашборда используется **Yahoo Finance API** (неофициальный, но покрывает и курсы валют, и цены ценных бумаг — используется в этом же под-проекте, не как задел на будущее).

Курсы получаются через интерфейс `RateProvider` (абстракция над источником курсов, чтобы заменить провайдера без изменения вызывающего кода) и кешируются в БД с таймстампом — чтобы не дёргать внешний API на каждый рендер и иметь fallback при его недоступности.

## Аутентификация и безопасность

- Email + пароль, хеш — **argon2id**.
- Сессии — **PostgreSQL** (отдельная таблица), не Redis: одна зависимость вместо двух, для локальной разработки и масштаба одного пользователя этого достаточно.
- Cookie: `httpOnly` + `secure` + `SameSite=Lax`.
- CSRF-защита (double-submit token) на все мутирующие запросы — необходимо, так как используются cookie-сессии.
- Rate limiting на `/login` и `/register` — защита от подбора пароля.
- Валидация всех входных данных на границе API через Zod.
- Изоляция данных: каждый запрос к БД фильтруется по `userId` владельца.
- Google OAuth — не сейчас, но `RateProvider`-подобная абстракция для auth-провайдера закладывается так, чтобы добавление Google auth не требовало переписывания модели User/Session.

## Тестирование

Vitest. Основной фокус модульных тестов в рамках фундамента — инвариант двойной записи (сумма дебета == сумме кредита, транзакция не создаётся при нарушении) и логика расчёта дельты при сверке остатков.
